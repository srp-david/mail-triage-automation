# 팀 분석 이력과 계정 소속

2026-09-28 사용자 결정에 따른 구현이다. 이번 작업은 로컬 변경·검증·커밋 범위이며 Supabase 적용, 설치본 교체, Release 게시, push는 하지 않는다.

## 보고서 권한

- 같은 팀의 활성 사용자는 모든 활성 출처의 분석 이력·보고서를 조회한다. 개인 출처·MCP·Agent 설정 없이 공용 분석 이력에 진입한다.
- 분석 사용자와 관리자는 팀 보고서를 편집하고 대화·질문을 등록할 수 있다. 조회 사용자는 읽기만 가능하다. 수정 버전, 작성자, 충돌 감지는 유지한다.
- 기존 `report_share` 값과 무관하게 팀에 공개된다. 팀 읽기 공유·편집 공유·공유 해제 버튼을 제거한다. 과거 공유 기록은 삭제하지 않는다. 구버전의 개별 공유 변경 요청은 `TEAM_SHARING_REQUIRED`로 거절한다.
- 다른 팀 보고서는 목록·상세·편집에서 차단한다. 계정 비활성화 후에도 그 계정이 남긴 보고서는 팀 자료로 남는다.
- 개인 출처의 원본 메일, 동기화, 실행기, 관련 메일/스레드 변경, 이전 문서 컬렉션과 지식 파일 반영 권한은 기존 경계를 유지한다. 팀 보고서 조회가 다른 PC의 원본 접근 권한을 부여하지 않는다.

## 메일함과 검색

공용 목록은 팀 전체 출처를 최신순으로 조회한다. 제목·현재 보고서 본문 검색, 분석 상태, 기간, 내가 분석한 이력 필터와 100건 단위 페이지 처리를 제공한다. 목록에는 작성자와 출처를 표시한다. API는 출처·작성자 UUID 필터도 지원한다.

메일함은 로컬 메일 ID와 팀 보고서의 메일 ID가 달라도 원본 헤더로 동일 메일을 확인한 후 연결한다. `Message-ID`, 발신자, 발송 시각, 제목으로 구성한 기존 fingerprint를 사용한다. 제목만 같은 메일을 합치지 않는다. 메일함 상태/이력 조회 전에 서버의 확인 기록을 최대 100개씩 조회하고, 미확인 메일만 최대 4개씩 병렬로 헤더를 읽어 연결한다. `011_mail_identity_checks.sql`의 확인 기록은 사용자·출처·MCP 인스턴스/연결 범위별로 보관하므로 1,000건을 넘어도 반복 검색이나 앱 재시작으로 전체 헤더를 다시 읽지 않는다. 이전 버전에서 연결된 메일도 해당 연결 범위의 확인 기록은 최초 한 번 생성한다. 실제 분석 상태와 권한은 매번 서버에서 조회한다.

헤더 부족도 정상적인 확인 결과로 24시간 보관한다. 조회 실패는 확인 성공으로 저장하지 않는다. 앱을 통한 동기화 배치가 끝나면 부분 성공/실패를 포함해 이전 확인 기록을 재사용하지 않으며, 다음 조회에서 다시 확인한다. 검색·조건 초기화·페이지 이동은 확인 기록을 재사용하고, 별도의 **메일 목록 새로고침** 버튼은 상태 필터 검색 대상 또는 전체 보기의 표시 메일을 재확인한다. 강제 재확인 실패 후 일반 조회에서도 예전 성공 기록으로 되돌아가지 않는다. 앱 외부에서 MCP의 기존 메일을 변경했다면 목록 새로고침으로 재확인해야 한다.

동일 메일로 확인된 팀 분석은 메일함의 분석 건수·완료 건수·최근 상태, 결과 보기, 이 메일 분석 이력, 팀 분석 보기에 함께 반영한다. 개인별 처리 완료는 다른 팀원에게 전파하지 않는다. 같은 사용자가 다른 출처에서 동일 메일을 조회하면 자신의 처리 완료는 유지하며, 취소는 연결된 동일 메일의 개인 표시를 함께 취소한다.

헤더가 없거나 다른 메일이면 자동 연결하지 않는다. 기존에 fingerprint가 등록되지 않은 이력도 원본 헤더 확인이 필요하다. 공용 목록에는 보이더라도 원본 연결 증거가 없는 보고서를 특정 메일에 추정 연결하지 않는다. 조회 실패와 분석 0건은 구분하여 안내한다.

## 팀과 계정 관리

- 초기 운영 팀은 개발1팀이다. 다른 팀은 자동 생성하지 않는다.
- `010_team_history.sql`은 `srp-tom`, `david`, `sara`의 기존 활성 소속 팀을 개발1팀으로 지정한다. 이미 동일 팀에 속한 계정들의 팀 이름을 변경하여 계정·팀·출처 UUID, 역할, 세션, 분석 자료를 보존한다. 계정을 새로 만들거나 비밀번호를 변경하지 않는다.
- 지정 계정들이 여러 팀에 분산되어 있거나 개발1팀 이름이 다른 팀에 이미 사용되면 마이그레이션 전체가 실패한다. 데이터 소유권을 임의로 옮기지 않고 운영자가 매핑을 확인해야 한다. 신규 DB에 대상 계정이 없다면 자동으로 만들지 않으며 bootstrap 시 초기 팀 이름을 개발1팀으로 설정한다.
- 서버 `TEAM_ID`로 지정한 초기 팀의 관리자가 팀을 추가하고 계정의 소속 팀을 지정한다. 추가된 팀의 관리자는 자기 팀 계정만 관리한다. 다른 팀의 보고서 조회 권한은 관리자에게도 자동 부여하지 않는다.
- 새 계정은 선택한 팀에 생성한다. 소속 팀 생략 시 관리자의 현재 팀을 사용한다. 기존 계정의 소속 변경은 변경 전·후 팀 관리 권한을 확인하고 모든 기존 로그인 세션을 폐기한다.
- 출처·실행기·이전 문서·분석 요청이 있는 계정은 일반 화면에서 팀을 변경하지 않는다(`USER_TEAM_HAS_DATA`). 자료 이관 범위를 정한 별도 작업이 필요하다. 마지막 활성 관리자의 강등·중지·팀 이동도 차단한다.

## 운영 반영 순서

이번 커밋은 운영 반영을 수행하지 않는다. 후속 배포 시 다음 순서를 따른다.

1. 지정 세 계정의 현재 membership과 `TEAM_ID`가 같은 초기 팀을 가리키는지 확인한다.
2. 기존 버전별 마이그레이션 절차로 `010_team_history.sql`, `011_mail_identity_checks.sql`을 적용하고 개발1팀 이름·계정 UUID·출처 귀속을 확인한다. 기존 마이그레이션 파일은 수정하지 않는다.
3. 새 공용 API를 배포한다. readiness는 `011_mail_identity_checks.sql` 적용을 요구한다. 기존 `/runs?sourceId=...` 요청과 일괄 메일 식별 요청은 유지하고, 출처별 `mail-identity-checks` API를 추가한다.
4. 새 PC 앱을 배포한다. 구버전 API에는 영속 확인 기록 조회 기능이 없으므로 PC 앱만 먼저 교체하지 않는다.
5. 두 사용자 PC에서 개인 설정 없는 공용 조회, 동일 메일의 팀 분석·태그, 개인 처리 완료 분리, 다른 팀 접근 차단을 실제 업무 사례로 확인한다.
